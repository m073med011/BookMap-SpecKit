# Implementation Plan: Authentication, Authorization, Roles, and Profiles

**Branch**: `002-auth-roles-profiles` | **Date**: 2026-04-23 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `specs/002-auth-roles-profiles/spec.md`

## Summary

Build the complete identity and access layer for the BookMap multi-vendor marketplace. This phase delivers: email/password registration with OTP verification, Google OAuth with PKCE flow, password reset for credentials users, role-based access control via JWT custom claims and RLS policies, profile management with avatar upload, staff invitation workflow, superadmin bootstrapping, and security event audit logging. All UIs support Arabic (RTL) and English (LTR) with dark/light theme.

## Technical Context

**Language/Version**: TypeScript 5.x with `strict: true`, Node.js 20+
**Primary Dependencies**: Next.js 15 (App Router), @supabase/ssr, @supabase/supabase-js, Zod, Tailwind CSS 4, shadcn/ui, next-intl, next-themes, goey-toast
**Storage**: Supabase PostgreSQL (profiles, roles, invitations, audit_logs tables) + Supabase Storage (avatars bucket)
**Testing**: Vitest (unit) + Playwright (E2E)
**Target Platform**: Web (modern browsers, SSR)
**Project Type**: Web application (Next.js App Router)
**Performance Goals**: <5s sign-in to dashboard, <3s profile update, <3min registration to verification
**Constraints**: Arabic RTL + English LTR, dark/light theme, all auth enforced server-side via RLS, PKCE flow for all OAuth/email flows
**Scale/Scope**: 6 database tables, 1 storage bucket, 7 auth pages, 1 profile page, 4 domain modules, 11 migrations

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Status | Notes |
| --------- | ------ | ----- |
| I. Domain-Driven Modular Architecture | PASS | Four domain modules: `features/auth/`, `features/profiles/`, `features/roles/`, `features/invitations/`. Each contains actions, components, schemas, services, types. Cross-domain imports through explicit public interfaces. |
| II. SOLID Principles & Clean Code | PASS | Auth actions separated from UI. Role-checking via typed `authorize()` function. Provider-specific logic (Google vs email) isolated in dedicated service functions. |
| III. Type Safety First | PASS | Zod validates all form inputs, server action params, and env vars. Supabase database types generated from schema. All action return types explicitly typed with discriminated unions. |
| IV. Security by Design | PASS | RLS on all tables. Server-side role validation in every server action. Avatar bucket with file type/size policies. No client-only security checks. Audit logging for all sensitive operations. PKCE for all auth flows. |
| V. Separation of Concerns | PASS | UI components contain no data-fetching. Server actions handle mutations. Repository pattern via typed Supabase service functions. Auth middleware separate from role-checking logic. |
| VI. Internationalization & Accessibility | PASS | All auth/profile UI uses externalized strings (en.json, ar.json). RTL-aware form layouts via Tailwind logical properties. Semantic HTML from Radix UI. |
| VII. Realtime with Durable Persistence | N/A | No realtime features in Phase 1. |
| VIII. Migration-Safe Incremental Delivery | PASS | All new tables (additive only). No modifications to Phase 0 schemas. Forward-compatible migrations. Stub libraries table for staff scoping (expanded in Phase 2). |

**Gate result**: PASS — all applicable principles satisfied.

**Post-design re-check**: PASS — data model, contracts, and project structure all comply. No violations.
